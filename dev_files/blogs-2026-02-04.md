## 1. Radio Shack's 2015 bankruptcy
**来源**: dfarq.homeip.net
**时间**: 12:00
**状态**: 未读
**原文链接**: https://dfarq.homeip.net/radio-shacks-2015-bankruptcy/

### 中文翻译

2015 年 2 月 5 日，Radio Shack 在连续 11 个季度亏损并累积 14 亿美元债务后，申请了第 11 章破产保护。虽然这不算是 Radio Shack 的正式终结，但今天的 Radio Shack 已经不再是过去的那个 Radio Shack 了。

虽然 Radio Shack 品牌依然存在，但已今非昔比。破产前的 Radio Shack 曾是电子爱好者和 DIY 玩家的圣地，提供各种电子元件、工具和设备。但多年来的战略失误、来自在线零售商的竞争以及未能适应数字化时代的变化，最终导致了它的衰落。

这提醒我们：即使是一个历史悠久且深受喜爱的品牌，如果不能适应市场变化和客户需求，也终将被淘汰。

## 2. We installed a single turnstile to feel secure
**来源**: idiallo.com
**时间**: 12:00
**状态**: 未读
**原文链接**: https://idiallo.com/blog/installed-single-turnstile-for-security-theater

### 中文翻译

被一家更大的公司收购后，安全成了首要任务。我们公司占据了三栋高楼，每栋至少 13 层。每个入口、每部电梯甚至停车场入口都安装了门禁读卡器，而停车场本身就高达 8 层。

首先启用的是停车场系统。如果你想停车，就需要刷卡。很快队伍就开始排起来了，但还算可控。

接着门禁系统也启用了。我经常把门禁卡忘在办公桌上，结果被困在楼梯间。午饭后，我爬楼梯到 11 楼，却发现被锁在门外。幸运的是，楼里人很多，总有人能帮我开门。我会可疑地溜进去，而他们则在想着邮件里明确说的——不要用自己的卡让别人进来。

当我们还在适应门禁卡时，公司正在每栋楼的一楼安装旋转闸机。它们看起来很未来感，但我已经预见到设计者没考虑到的问题。每栋楼有 13 层，每层都满是员工。每栋楼数百名员工都需要刷卡进入。

我是一名软件工程师。我明白安全不是你可以在应用程序之上构建的可选功能。相反，你需要在基础层面就实现安全措施。实际上，我正在开发的最重要的一个应用就是一个工具，用于管理不同团队如何从 Jira 获取任务。

不管怎样，这个应用的原始设计者当时肯定时间紧迫。应用的每个操作都需要调用 Jira 端点，这需要身份验证。他从未保存 API 返回的认证令牌。相反，每次调用都需要重新认证，然后再执行任务。

他有没有让用户每次都重新输入密码？没有，他比那聪明。他把凭证以明文保存在数据库里了吗？他可能是个实习生，但他并不疯。不！相反，他把用户名和密码保存在 cookie 里。但为了让情况更好些，他用 base64 编码了。

最终，我们收到了邮件。所有的旋转闸机都将启用。接下来的周一，它们将以模拟模式运行，闸机会保持开启，但我们必须刷卡，等待哔声和绿灯后才能进入。

我早上 8:30 到达。我在大厅遇到了我的同事和数百名其他员工。当第一个人刷卡时，机器发出哔声并亮起绿灯。我们都鼓掌庆祝。我们轮流走到机器前。哔、绿灯、下一个。但对一些员工它发出抱怨声并亮起红灯。不过没关系，这是模拟日。我们继续工作。

第二天，当我来上班时，我在车里被困在停车场排队至少 10 分钟。往外看，我看到每栋楼外都排着长队。

我设法停了车，发现排队的人一直延伸到停车场楼层。我排队等了至少 30 分钟才到大堂。我给经理发短信说，我会因为被困在队伍里而错过每日站会。她没有回短信。相反，她从队伍前面向我挥手。刷卡已经很慢了，你需要等待批准。但一旦你通过旋转闸机，还有另一个电梯队伍。电梯的门禁读卡器也启用了。

想象一下，几十个人都想挤进拥挤的电梯，每个人去不同的楼层，每个人都试图刷卡进入自己的楼层，因为未经授权的人不能替他们刷卡。一些电梯门打开时，里面已经有几个人了，因为他们无法在人群中刷卡，所以又回到一楼进行第二次尝试。换句话说，完全是一团糟。

从停车场到我 11 楼的办公桌花了超过一个小时。

第三天，我决定节省时间，打车上班。那时候一趟 Uber 只要 3 美元。我以为自己很聪明，但另外大约一百人也有同样的想法。我们有大量 Uber 车在外面排队，每辆都试图让乘客下车，挡住了通往停车场的路，造成了又一次交通拥堵。大楼里依然是一片混乱。我只节省了几分钟。

第三天，他们关闭了旋转闸机。它们显然不行。他们还禁用了电梯里的门禁读卡器。大家都松了一口气。

安全本应是优先事项，但从没有人讨论过保存在 cookie 里的 Jira 凭证。当我请求安装 Redis 服务来存储生成的认证令牌时，我遇到了巨大的阻力。我不得不写整篇文档来证明使用它的合理性，并向供应商申请企业支持。一个月后，安全问题在无人注意的情况下被修复了。

然而，我们确实收到了一封庆祝大堂安装三个新旋转闸机的邮件。他们再也没有重新启用电梯里的门禁读卡器。它们一直处于休眠状态，提醒着我们所经历的那场混乱。

旋转闸机是看得见的。它们很贵。它们扰乱了每个人的一天，并成为公司范围邮件中的头条新闻。管理层可以指着它们说，我们正在认真对待安全。与此同时，数千名员工的 Jira 凭证被存储在 cookie 中。这是一个可能暴露我们整个项目管理系统的漏洞。但这修复需要文档、供应商批准、一个月的说服工作。还有大量的乞求。

安全剧场可以打勾。它让人们觉得正在采取措施。真正的安全是看不见的。它是代码审查、实现适当的身份验证、正确存储令牌。它没有剪彩仪式或庆祝邮件。它只是好的工程实践，做对时没人注意到。但安全剧场却不可能被忽视。

## 4. I prefer to pass secrets between programs through standard input
**来源**: utcc.utoronto.ca/~cks
**时间**: 04:12
**状态**: 未读
**原文链接**: https://utcc.utoronto.ca/~cks/space/blog/programming/PassingSecretsViaStdin

### 中文翻译

在 Unix 系统上，有多种方式可以在程序之间传递机密，其中很多方式在某些情况下可能会暴露你的机密。通过命令行传递的机密在进程列表中可见；通过环境变量传递的机密可以在进程的环境中找到（通常可以被外部方检查）。当我在[我们的环境](https://support.cs.toronto.edu/)中的管理程序中不得不处理这个问题时，我选择了一个老牌的 Unix 备用方案：通过文件描述符在程序之间传递机密，特别是标准输入和标准输出。这甚至可以在 shell 脚本中使用和完成。然而，显然需要一些注意事项，无论是在一般情况下还是在 shell 脚本中。

虽然 Bourne shell 脚本变量看起来像环境变量，但直到你用 '`export`' 要求时，它们才会被导出到环境中。当然，对于保存机密的环境变量，你永远不应该这样做。另外，如今 'echo' 是你想使用的任何版本的 Bourne shell 的内置命令，所以 '`echo $somesecret`' 实际上不会运行一个在命令行参数中可见机密的进程。然而，你必须小心你在这里使用的命令，因为像 [`printf`](https://www.gnu.org/software/coreutils/printf) 这样可能方便的都不是内置的，不能这样使用。

作为一般注意事项，你需要限制机密中允许的字符，或者以某种方式对机密进行编码（你不妨使用 base64）。如果你需要通过这种方式在程序之间传递多个东西，你需要定义一个非常小的协议，如果只是为了写下程序之间发送东西的顺序的话（例如，如果它们是换行符分隔的）。

通过这种方式传递机密的一个好处是，通过像 SSH 这样的机制（如果你有无密码 SSH）很容易在机器之间传递它们。与其 'provide-secret | consume-secret'，你可以简单地改为 'provide-secret | ssh remote consume-secret'。

在合适的（Unix）环境中，可以使用像 Bash 的 '`<(...)`' 符号或支持 Bash 功能的底层 Unix 功能（特别是，/dev/fd）这样的功能，通过这种方式将机密传递给想要从文件中读取它们的程序。

通过这种方式在程序之间传递机密可能看起来有点拙劣和不恰当，但我可以作证它有效。我们有许多东西以这种方式移动机密，包括跨机器，而且它们多年来一直这样做，没有问题。

（在 Linux 上，有一些花哨的方式来处理某些类型的机密，通常是静态机密，但我不知道有其他一般可用的方式来处理动态生成的机密，特别是如果一些机密使用者是 shell 脚本的话。但你可能会写一个基于 D-Bus 的系统来用各种花哨功能来做这件事，如果你必须经常这样做并想要一些看起来更专业的东西。）

### 中文翻译

我通过阅读 Sebastian Raschka 的《从零开始构建大语言模型》一书来结束我的系列文章，想看看我能否在自己的硬件上训练出尽可能好的基础模型。我开始是在我的 RTX 3090 上训练一个，发现虽然它是一个不错的小模型，但不如原来的 GPT-2 small，无论是在测试数据集上的损失，还是在经过指令微调后遵循指令提示的能力方面。我决定想看看我能拉动哪些杠杆——dropout、注意力权重偏置等等——来让它变得更好。

为此，我不想让我的电脑在多次长时间训练中被占用几天，所以我学习了如何在云端更快地训练。这导致了我使用的提示跟随测试的一些改进，我还花了一些时间进行了一个支线任务，将我训练的各种模型上传到 Hugging Face Hub。

现在是时候尝试各种"干预"了，我这么称呼这些拉动看看是否能改进模型的杠杆。这篇文章是回顾它们是什么，并描述我为建立基准模型所做的努力。训练完整地进行了，最终训练损失为 3.743，以及一个合理的测试损失。这些实验将作为未来干预的比较基准。

## 9. New York Tech at 30: the Crossroads
**来源**: anildash.com
**时间**: 00:00
**状态**: 未读
**原文链接**: https://anildash.com/2026/02/03/nye-tech-30/

### 中文翻译

过去一周，在一系列活动上，纽约科技界庆祝了一个模糊概念的 30 周年——"Silicon Alley"，这个通用术语指代我们更大的创作者和合作者、创始人和资助者、发明者和投资者、教育者和企业家以及民选官员、活动家和建筑师以及艺术家的集体。一些派对或交流会都是典型的行业活动，通常都是关于交易和客套话的寒暄。但很多都更深层次，反思我们在纽约建立的社区有什么特别和有意义的地方。[Steven Rosenbaum 的反思](https://www.mediapost.com/publications/article/412470/) 很好地捕捉到了这一点，而 [Leo Schwartz 为《财富》杂志撰写的文章](https://finance.yahoo.com/news/silicon-alley-turns-30-york-114752768.html) 则涵盖了更传统的商业角度。

除了庆祝，我还想反思这几天我进行的几次深刻对话。这些对话基于我们国家和城市今天的现实，远超富裕的科技从业者参加派对和互相庆祝的空间。这些对话中提出的难题决定了这个社区未来的走向，它们是在当前时刻每个科技社区都将面临的问题。

我知道纽约市科技社区曾经是什么；有一段时间，我是它最突出的声音之一。现在的问题是，它未来将成为什么。因为我们正处于一个深刻的十字路口。
